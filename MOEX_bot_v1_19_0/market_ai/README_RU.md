# MOEX Market AI — отдельный исследовательский блок

Это новая автономная подсистема для проверки гипотезы: можно ли по последним 60 минутным свечам оценивать вероятность движения цены **вниз / боковик / вверх** на нескольких горизонтах. Она не заменяет `local_learning.py`, не меняет фильтры скальпера и не отправляет ордера.

## Что именно реализовано

- **Один входной ряд:** последние 60 минутных OHLCV-свечей одного инструмента.
- **12 признаков на каждой минуте:** лог-доходность, тело свечи, диапазон, верхняя/нижняя тень, положение close внутри диапазона, логарифм объёма, z-score объёма за 30 свечей, промежуток между свечами, время суток (sin/cos) и отклонение snapshot-цены от последней закрытой свечи (для событий Supervisor).
- **7 выходных голов:** 1, 5, 10, 30, 60, 180 и 300 минутных свечей вперёд.
- **3 класса:** `DOWN`, `FLAT`, `UP`. `UP` означает, что рост превысил заданную оценку полных round-trip издержек. `DOWN` — падение сильнее той же величины. Остальное — `FLAT`.
- **Сравнение четырёх подходов:** Logistic Regression, HistGradientBoosting, MLP и GRU. Простые модели нужны как контроль: более сложная нейросеть не считается лучше только потому, что она нейросеть.
- **Защита от утечки будущего:** торговые даты делятся последовательно 70% train / 15% validation / 15% test. Случайный train/test split не используется. Масштабирование рассчитывается только на train.
- **Ранняя остановка:** MLP/GRU выбирают эпоху по validation loss. Test не используется для выбора эпохи или модели.
- **Отдельная оценка торговли:** помимо accuracy выводятся balanced accuracy, macro-F1, recall классов, precision сигналов UP, число/доля сигналов и средний net-return этих сигналов после заданных издержек.

## Откуда брать данные

### Предпочтительный источник: история Т-Инвестиции

В проект добавлен `fetch_tbank.py`. Он использует уже имеющийся у бота API-токен через переменную окружения, а не сторонний платный сервис. Для 1-минутного `GetCandles` официальный API указывает максимальный период запроса до одного дня и лимит 2400 свечей; поэтому загрузчик делает отдельный запрос на каждый инструмент/день и соблюдает паузу между запросами. Глубина истории зависит от инструмента; API возвращает дату первой доступной минутной свечи в справочных методах.

Пример на машине, где есть действующий токен Т-Инвестиции:

```bash
pip install -r requirements_market_ai.txt
read -rsp 'T-Invest API token: ' TINKOFF_TOKEN; echo
export TINKOFF_TOKEN
python -m market_ai.fetch_tbank \
  --from 2026-08-01 --till 2026-11-19 \
  --tickers SBER,GAZP,LKOH,ROSN,VTBR,T,YDEX,MOEX,AFLT,FLOT \
  --out data/market_ai/tbank_1m.csv
unset TINKOFF_TOKEN
```

Тикеры по умолчанию запрашиваются как `TICKER_TQBR`. При необходимости можно сменить `--suffix`, например для другого класса инструмента, либо передать идентификаторы вида `TICKER_CLASS` в `--tickers`. Если API сообщает, что инструмент не найден, проверьте точный `instrumentId`/класс в Т-Инвестициях. Ошибки отдельных дней записываются в соседний `.errors.txt`, частично скачанные данные сохраняются.

Ограничения глубины истории и допустимые интервалы описаны в официальной документации Т-Банка: [GetCandles](https://developer.tbank.ru/invest/api/market-data-service-get-candles), [Исторические котировки](https://developer.tbank.ru/invest/intro/intro/load_history), [FAQ по глубине истории и ограничениям](https://developer.tbank.ru/invest/services/quotes/faq_marketdata/).

### MOEX ISS

Есть дополнительный `fetch_moex.py` для прямой загрузки свечей ISS. Но нельзя заранее обещать, что анонимная сессия вернёт исторические данные: в документации MOEX отдельно указано, что исторические данные без авторизации могут быть недоступны, а бесплатный доступ с задержкой относится не ко всем блокам данных. Если ISS вернёт ошибку/пустую историю, используйте выгрузку Т-Инвестиции или свой лицензированный экспорт. См. [официальную страницу ISS](https://www.moex.com/a8531) и [руководство ISS](https://www.moex.com/files/4be999zbzp80bx2bgmwayrtyx0).

### FI-2010 как внешний research benchmark

FI-2010 — известный открытый benchmark order-book прогнозирования: примерно 4 млн наблюдений по пяти акциям Nasdaq Nordic за 10 торговых дней. Он полезен для проверки архитектур и методики, но **не смешивается с MOEX** в этой реализации: другой рынок, инструменты, микроструктура и период. При обучении на FI-2010 можно получить красивую метрику, не имеющую прямого отношения к MOEX. Источник: Ntakaris et al., [Benchmark Dataset for Mid-Price Forecasting of Limit Order Book Data with Machine Learning Methods](https://arxiv.org/abs/1705.03233), [описание датасета](https://etsin.fairdata.fi/dataset/73eb48d7-4dbc-4a10-a52a-da745b47a649).

## Обучение

```bash
python -m market_ai.train \
  --csv data/market_ai/tbank_1m.csv \
  --sqlite data/supervisor.sqlite3 \
  --out data/market_ai/run_$(date +%Y%m%d_%H%M) \
  --round-trip-cost-pct 0.20 \
  --epochs 10 --batch-size 512
```

`--round-trip-cost-pct 0.20` — пример, а не универсальная комиссия. Укажите реалистичную сумму **комиссии покупки + комиссии продажи + спреда + проскальзывания** именно для своего счёта и ликвидности. Если эта величина ошибочна, классы и результат оценки тоже будут ошибочными.

Если тестируете на маленьком наборе/слабой машине, уменьшите потребление ресурсов:

```bash
python -m market_ai.train --csv data/market_ai/tbank_1m.csv \
  --sqlite data/supervisor.sqlite3 --out data/market_ai/run_small \
  --sequence-length 30 --sample-stride 8 --batch-size 128 \
  --epochs 5 --models gru,logistic
```

Для надёжного сравнения желательно иметь не менее 30–60 торговых дат и несколько ликвидных тикеров. При трёх датах скрипт технически сможет сделать split, но оценки будут очень шумными. 1m GetCandles может не содержать одинаковую глубину для всех бумаг.

## Как учитываются упущенные ямы

Если передан `--sqlite`, подсистема читает `samples` из `supervisor.sqlite3` и пытается сопоставить события с исторической минутной последовательностью того же тикера и даты. Нужны доступные свечи и сохранённый зрелый исход.

- `missed=1`: дополнительный обучающий пример для головы **5m**, вес `2.0`; успешная пропущенная цель становится UP, HOLD — FLAT.
- Фактическая сделка (`ml_source=actual` или `stage=bought`): метка строится по фактическому net P&L, вес `1.5`.
- Другие зрелые контрфактические примеры: вес `1.0`.
- Близкие события одного тикера дедуплицируются с окном `--event-horizon-seconds` (по умолчанию 300 секунд), чтобы десятки повторных snapshot одной ямы не превратились в десятки независимых удачных сделок.
- SQLite-разметка текущего Supervisor имеет собственный короткий lookahead (обычно 300 секунд). Поэтому её **не переносят** на 30m/1h/3h/5h. Для этих горизонтов целевые метки строятся непосредственно по будущим свечам.

Счётчик Telegram «потенциально пропущенных прибыльных входов» не читается как количество независимых сделок. Для обучения нужны уникальные события, соответствующая последовательность до момента события и зрелый будущий исход.

## Что появляется после обучения

В выбранной папке запуска:

- `REPORT_RU.md` — краткий отчёт по тестовой части;
- `report.json` — метрики, разбиение по датам, частоты классов, параметры и предупреждения;
- `metrics.csv` — сравнение моделей по каждому горизонту;
- `gru_multi_horizon.pt`, `mlp_multi_horizon.pt` — веса нейросетей и их scaler;
- `comparison_models.joblib` — обученные sklearn baseline-модели;
- `scaler.npz` — статистики нормализации.

## Получение прогноза

```bash
python -m market_ai.predict \
  --model data/market_ai/run_YYYYMMDD_HHMM/gru_multi_horizon.pt \
  --csv data/market_ai/tbank_1m.csv \
  --out data/market_ai/predictions.csv
```

Команда выдаёт последнюю последовательность по каждому тикеру: вероятности DOWN/FLAT/UP для семи горизонтов. `BUY_CANDIDATE` — лишь исследовательский порог `P(UP) >= 0.60` и `P(UP)-P(DOWN) >= 0.10`, а не реальная команда покупки.

## Почему здесь GRU, а не большой Transformer

Обучающий набор пока ограничен историей, доступной для минутных свечей и текущей телеметрией Supervisor. Небольшой GRU — разумный первый sequence baseline; MLP позволяет проверить, действительно ли порядок последних свечей добавляет ценность. TFT и DeepLOB — полезные научные ориентиры, но полноценный TFT требует более сложной конструкции covariates/attention, а DeepLOB рассчитан на структурированный поток уровней limit order book, которого нет в обычных OHLCV-свечах. Поэтому модель не выдаётся за репликацию этих работ.

Литература:

1. Zhang, Zohren, Roberts, [DeepLOB: Deep Convolutional Neural Networks for Limit Order Books](https://arxiv.org/abs/1808.03668), 2018/2020 — CNN+LSTM для последовательностей состояния стакана.
2. Lim et al., [Temporal Fusion Transformers for Interpretable Multi-horizon Time Series Forecasting](https://arxiv.org/abs/1912.09363), 2019/2021 — multi-horizon прогнозирование с recurrent layers и attention.
3. Ntakaris et al., [FI-2010 benchmark](https://arxiv.org/abs/1705.03233) — day-based time split для рыночных последовательностей.

## Важные ограничения

- На момент сборки архив содержит **код обучения**, а не обученную на твоих рыночных данных модель: в текущем сообщении нет CSV свечей и самого `supervisor.sqlite3`, только Telegram-сводка. Реальные метрики появятся после команды обучения на доступной истории.
- Accuracy не равна прибыльности. Смотри особенно `UP precision`, количество сигналов, средний net-return, комиссии, spread/slippage и устойчивость по разным датам/тикерам.
- 1m horizon — одна следующая доступная минутная свеча. При пропусках времени это может быть чуть больше 60 секунд; разрывы, слишком большие для соответствующего горизонта, маскируются.
- Горизонты 180m/300m считаются по количеству свечей в пределах одной торговой даты, без переноса через ночь. Они не равны прогнозу календарного времени на 3/5 часов при остановках/паузаx в ленте.
- Доступность минутной истории разнится по инструментам. Несколько месяцев × несколько тикеров обычно полезнее, чем десятки минут данных по одной акции.
- Текущая стратегия не меняется. Не подключайте модель к отправке ордеров до отдельного paper-trading, проверки исполнения/издержек и достаточного числа независимых тестовых сделок.
